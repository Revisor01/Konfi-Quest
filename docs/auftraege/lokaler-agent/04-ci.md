# 04 — CI und Workflows

Grundlage: `docs/audit/2026-09-26/ci-deployment-store.md` (lies die Befunde
vollständig, inklusive Status-Zeilen) und für die Sitemap
`dokumentation-gegen-code.md` BF-13. Basis ist `main` **nach** dem Merge von
2.3.0. Jede Änderung auf einem eigenen Branch, Pull Request, CI grün. Für
Workflow-Dateien braucht es das Recht „Workflows" — das hat der lokale
Agent, die Cloud-Sitzungen haben es nicht.

Reihenfolge nach Nutzen; jeder Punkt ein eigener Commit.

## 1. Deploy-Reihenfolge (BF-04, Rest)

`concurrency: deploy-production` verhindert gleichzeitige Deploys. Offen:
Braucht ein älterer Push länger für seine Tests, deployt er **nach** dem
neueren und setzt den älteren Stand.

- [ ] Im `deploy`-Job vor dem Tausch prüfen, dass `GITHUB_SHA` der jüngste
      Commit auf `main` ist (oder dessen Vorfahre nicht ist) — sonst mit
      klarer Meldung überspringen, nicht fehlschlagen.
- [ ] `cancel-in-progress: true` für Test-Jobs auf Refs außer `main`.
- [ ] Gegenprobe beschreiben (zwei Pushes kurz hintereinander, der ältere mit
      künstlich langsamem Test), Ergebnis mit Zeiten.

## 2. Rotes `main` meldet sich (BF-07, Rest)

Heute nur GitHubs Standard-Mail an den Committer.

- [x] Simon fragen, wohin: Mail, Push, Issue. Dann ein Schritt `if: failure()`
      auf `main`, der genau dorthin meldet. Kein Geheimnis im Repo — Ziel über
      ein Actions-Secret.
      **Ergebnis 29.09.2026 (Repo):** Simon: Issue. Eigener Workflow
      `ci-meldung.yml` (`workflow_run` auf „CI Pipeline", nur push auf `main`)
      statt eines Schritts in `ci.yml` — er kann weder das Ergebnis von `ci.yml`
      (Release-Tor) noch den Deploy berühren; Begründung im Kopf der Datei.
      `.github/scripts/ci-meldung.py` gleicht ein Issue mit Label
      `ci-rot-main` mit dem jüngsten fertigen Lauf ab (rot: anlegen oder
      ergänzen, grün: schließen). Kein Geheimnis nötig. **Offen:** erster echter
      Lauf auf GitHub (erst nach dem Merge wirksam).

## 8. Sicherheits-Header im Web (BF-14)

- [x] `Referrer-Policy`, `Permissions-Policy`, `X-XSS-Protection` entfernen;
      CSP erst als `Content-Security-Policy-Report-Only`, eine Woche
      beobachten, dann scharf. Ionic/Vite brauchen evtl. `style-src 'unsafe-inline'`
      — messen, nicht raten.
      **Ergebnis 29.09.2026 (Repo):** in `frontend/nginx.conf` umgesetzt, die
      CSP der Web-App (`$csp_app`) als Report-Only auf dem SPA-Rückfall.
      Lokal gegen das gebaute Image und ein Test-Backend in Chromium an 21
      Stationen (Anmeldung, Reiter von Konfi, Org-Admin und Team, Chat mit
      Bild, PDF-Ansicht): erst 24 Meldungen (`connect-src` für `data:` aus
      Ionicons und `blob:` aus der PDF-Ansicht), nach der Ergänzung 0 — auch
      mit scharf geschalteter Policy. `style-src 'unsafe-inline'` ist nötig
      (Ionic, Swiper).
- [ ] Nach dem Deploy eine Woche beobachten: In Chrome mit offenen
      Entwicklerwerkzeugen die Web-App unter der öffentlichen Adresse
      durchgehen und die Konsole nach „Content Security Policy" filtern —
      besonders, was lokal **nicht** geprüft ist: QR-Scanner im Browser,
      Sprachaufnahme bei einer Challenge, Rückblick als Bild speichern,
      Material mit Links und Dateien, Tageslosung, Anmeldung über einen
      Einladungslink. Jede Meldung mit Direktive und blockierter Adresse
      notieren (ohne Tokens aus Adressen).
- [ ] Ohne Meldung: in `frontend/nginx.conf` den Header-Namen
      `Content-Security-Policy-Report-Only` in `Content-Security-Policy`
      ändern (Test `sicherheitsHeader.test.ts` mitziehen) und per Pull
      Request ausrollen. Mit Meldung: Quelle in `$csp_app` ergänzen, begründen,
      Test ergänzen, weiter beobachten.
