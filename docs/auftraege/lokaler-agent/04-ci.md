# 04 — CI und Workflows

Grundlage: `docs/audit/2026-09-26/ci-deployment-store.md` (lies die Befunde
vollständig, inklusive Status-Zeilen) und für die Sitemap
`dokumentation-gegen-code.md` BF-13. Basis ist `main` **nach** dem Merge von
2.3.0. Jede Änderung auf einem eigenen Branch, Pull Request, CI grün. Für
Workflow-Dateien braucht es das Recht „Workflows" — das hat der lokale
Agent, die Cloud-Sitzungen haben es nicht.

Reihenfolge nach Nutzen; jeder Punkt ein eigener Commit.

## 1. Deploy-Reihenfolge (BF-04, Rest)

`concurrency: deploy-production` verhindert gleichzeitige Deploys. Offen:
Braucht ein älterer Push länger für seine Tests, deployt er **nach** dem
neueren und setzt den älteren Stand.

- [x] Im `deploy`-Job vor dem Tausch prüfen, dass `GITHUB_SHA` der jüngste
      Commit auf `main` ist (oder dessen Vorfahre nicht ist) — sonst mit
      klarer Meldung überspringen, nicht fehlschlagen.
      **Ergebnis 29.09.2026 (Repo, Großpaket):** `deploy/rollend.sh` mit
      `NUR_VORWAERTS=1` überspringt einen älteren Stand grün mit
      `::notice::Deploy uebersprungen`. Im Deploy-Log vom 29.09. zu sehen:
      „Vorwaerts-Pruefung: live … ist aelter oder abgezweigt -> ausrollen".
- [x] `cancel-in-progress: true` für Test-Jobs auf Refs außer `main`.
      **Ergebnis 29.09.2026 (Repo, Großpaket):** umgesetzt (`concurrency` je Ref, auf `main` je SHA).
- [ ] Gegenprobe beschreiben (zwei Pushes kurz hintereinander, der ältere mit
      künstlich langsamem Test), Ergebnis mit Zeiten.
      **Stand 30.09.2026:** lokal gegen eine nachgebaute Portainer-API geprüft
      (`frontend/src/__tests__/betrieb/rollenderDeploy.test.ts`); der erste
      echte Überholfall auf GitHub steht aus — nur beobachten, nicht erzwingen.
